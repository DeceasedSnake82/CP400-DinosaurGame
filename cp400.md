# Making games for the fx-CP400 (Hollyhock 3) - field guide

Everything you need to know to write a game for the Casio fx-CP400 / ClassPad II with
[Hollyhock 3](https://github.com/classpaddev/hollyhock-3), collected while building this Dino game
(and from the Chess and Game of Life projects). Anything marked **(unverified)** is not confirmed on real
hardware; the rest comes from the SDK headers, the SDK docs, or was exercised by the host tests in this repo.

---

## 1. The 30-second picture

| | |
|---|---|
| CPU | SuperH **SH-4A**, **big-endian**, **no FPU** (`sh4a_nofpueb`): `float`/`double` are software-emulated and very slow |
| Screen | **320 x 528**, portrait, 16-bit **RGB565**, touch screen |
| Framebuffer | a plain `uint16_t[320*528]` at `0x8C000000` (`vram` in `calc.h`, or `LCD_GetVRAMAddress()`); nothing shows until you push it with `LCD_Refresh()` |
| Heap | 12 MB (`0x8C280000` - `0x8CE80000`), via `Mem_Malloc` / `Mem_Free` |
| OS services | function pointers resolved at load time by the Hollyhock launcher (`extern int (*GetInput)(...)`) |
| App format | `.hh3` = a **stripped ELF** with `.note.hollyhock` metadata (`APP_NAME`, ...). Copy it to the calculator and start it from the Hollyhock launcher |
| Timer | **none in the SDK** (see section 6 - this shapes game design) |
| Sound | none in the SDK |
| Exit | your `main()` returns; give the player a key to do that (the Power/Clear key is the convention) |

Hollyhock 3 is for fx-CP400, fx-CP400+E and fx-CG500. Newer hardware revisions (ABS_Date 2022) need OS >= 2.01.7002;
read the compatibility section of the hollyhock-3 README before telling anybody to install it. Flashing is at your own risk.

## 2. Toolchain and build

* Compiler: `sh4a_nofpueb-elf-gcc/g++` (crosstool-ng build with a newlib port). Easiest source is the Docker image
  `ghcr.io/classpaddev/hollyhock-3:v2.2.2`, which contains the toolchain in `/toolchain/bin` and the built SDK in `/sdk`
  (`SDK_DIR=/sdk`). Building the toolchain from scratch is a long job (see `QBos07/CP-dockercross`), so use the image.
* `make` produces `Name.elf`, then `strip` turns it into `Name.hh3`. All three CP400 projects use the same Makefile; the important flags:
  ```make
  FUNCTION_FLAGS = -flto -ffat-lto-objects -ffunction-sections -fdata-sections -O2 -gdwarf-5
  CXX_FLAGS      = $(FUNCTION_FLAGS) -std=gnu++17 -Wall -Wextra -fno-exceptions -fno-rtti -I $(SDK_DIR)/include/
  LD_FLAGS       = $(FUNCTION_FLAGS) -Wl,--gc-sections -L$(SDK_DIR)      # link with: ... $(OBJECTS) -lsdk
  ```
  `-fno-exceptions -fno-rtti` keeps the binary small. The Makefile picks up every `*.cpp/*.c/*.S` in the folder.
* Metadata at the top of one source file (all optional):
  ```cpp
  #include <appdef.h>
  APP_NAME("Dino")  APP_DESCRIPTION("...")  APP_AUTHOR("you")  APP_VERSION("1.0.0")
  ```
* CI recipe (GitHub Actions): run the build inside the container image, upload `*.hh3` as an artifact:
  ```yaml
  container: { image: "ghcr.io/classpaddev/hollyhock-3:v2.2.2", credentials: { username: "${{ github.actor }}", password: "${{ secrets.github_token }}" } }
  steps: [ { uses: actions/checkout@v4 }, { run: make -j }, { uses: actions/upload-artifact@v4, with: { path: "*.hh3" } } ]
  ```
* Standard library: newlib is part of the toolchain image, but the SDK also gives you `String_*` and `Mem_*`. Prefer small
  hand-written helpers (`putInt`, `putStr` in `gfx.cpp`) over `printf` - smaller and no float formatting code.
* Static state (globals, `static` arrays) is fine and the best option for games: no heap, no fragmentation, no `NULL` checks.
  Global constructors run (the SDK itself uses them: `calcInit` backs up VRAM at start, `calcExit` restores it and refreshes the
  LCD when your app ends), but keep them trivial.

## 3. SDK API cheat sheet

Include what you use: `<sdk/os/lcd.h>`, `<sdk/os/input.h>`, `<sdk/os/mem.h>`, `<sdk/os/file.h>`, `<sdk/os/debug.h>`, `<sdk/calc/calc.h>`...
Everything is a **function pointer** (`extern void (*LCD_Refresh)();`), so calls cost an indirect jump and cannot be inlined.

### Display (`lcd.h`, `calc.h`)
| Call | Notes |
|---|---|
| `uint16_t* LCD_GetVRAMAddress()` / `vram` (calc.h) | the framebuffer; row-major, `y*320 + x` |
| `LCD_Refresh()` | copies **all of VRAM** to the panel. Blocks for the whole transfer: this is the frame-time floor of every game |
| `LCD_ClearScreen()` | fills VRAM with white (no refresh) |
| `LCD_SetPixel/GetPixel`, `LCD_SetPixelFromPalette` | slow (function call per pixel); write VRAM directly instead |
| `LCD_VRAMBackup()/LCD_VRAMRestore()` | save / restore VRAM (the SDK start-up and exit code already do this for you) |
| `LCD_SetDrawingBounds(x0,x1,y0,y1)` + `LCD_SendCommand(COMMAND_PREPARE_FOR_DRAW_DATA)` + writes to `*lcd_data_port` (`0xB4000000`) | documented as the way to do **partial updates**: push only a window. **(unverified)** whether the end coordinates are inclusive and whether the panel axes match VRAM on every model. This repo ships it as an opt-in "LCD: FAST" setting for that reason |
| `fillScreen`, `line`, `vline`, `triangle`, `setPixel` (calc.h) | convenience software drawing into VRAM; fine for prototypes, too slow for a game loop |
| `color(r,g,b)` (calc.h) | **has a bug**: the blue mask is `0x001A` instead of `0x001F`, so blue loses bits. Use your own `rgb565` helper: `((r&0xF8)<<8) | ((g&0xFC)<<3) | (b>>3)` |
| `RGB_TO_RGB565(r5,g6,b5)` (lcd.h) | takes already-reduced 5/6/5-bit components |

Drawing text: the OS "debug" font (`Debug_Printf(x, y, invert, 0, fmt, ...)`, `Debug_PrintString`, 8x12 cells, 40 columns x 37 rows)
works but is only black-on-white/inverted; games usually ship their own bitmap font (5x7 in `gfx.cpp`, scaled by integers).
`Debug_WaitKey()` blocks until a digit key / Power-Clear (or a touch on OS >= 7002).

### Input (`input.h`)
```cpp
struct Input_Event ev;                       // packed struct: ZERO IT before every call (Mem_Memset or a byte loop)
GetInput(&ev, 0 /*poll*/ or 0xFFFFFFFF /*block until something happens*/, 0x10);   // always returns 0; read ev.type
```
* `ev.type`: `EVENT_KEY`, `EVENT_TOUCH`, `EVENT_NONE` (queue empty), plus `EVENT_TIMER` and action-bar events; ignore anything you do not know.
* Key event: `ev.data.key.direction` is `KEY_PRESSED` / `KEY_HELD` / `KEY_RELEASED`, `ev.data.key.keyCode` is `KEYCODE_*`
  (`KEYCODE_UP/DOWN/LEFT/RIGHT`, `KEYCODE_EXE`, `KEYCODE_POWER_CLEAR`, `KEYCODE_0..9`, `KEYCODE_PLUS/MINUS/TIMES/DIVIDE`, `KEYCODE_DOT`,
  `KEYCODE_EQUALS`, `KEYCODE_BACKSPACE`, `KEYCODE_SHIFT`, ...). Act on `KEY_PRESSED` only unless you want auto-repeat.
* Touch event: `ev.data.touch_single.direction` (`TOUCH_DOWN`, `TOUCH_HOLD_DRAG`, `TOUCH_UP`), `p1_x`, `p1_y` in screen pixels (**can be negative or past the
  edge**). Use the multi-touch union member only if you check for it; a single finger is the normal case.
* Polling held keys: `Input_GetKeyState(ScancodeUp)` (true while down; `Scancode*` constants, **not** `KEYCODE_*`), `Input_IsAnyKeyDown()`.
  Pattern used here: events *latch* quick taps ("jump pressed this frame"), polling gives "is it still held" (variable jump height, ducking).
* Legacy `getKey(&k1,&k2)` in `calc.h` reads the key matrix directly (hardware registers) - fine for fast polling, no events.
* Drain the queue each frame: loop `GetInput(..., 0, 0x10)` until `EVENT_NONE` (cap the loop at ~32 so a flood cannot stall a frame).
* **Block when idle**: if nothing animates (menu, pause), call `GetInput(&ev, 0xFFFFFFFF, 0x10)` so the CPU sleeps instead of spinning.

### Memory (`mem.h`)
`Mem_Malloc(n)` / `Mem_Free(p)` (12 MB heap), `Mem_Memcpy`, `Mem_Memset`, `Mem_Sbrk`. For a game, prefer static arrays. Remember `Input_Event` needs zeroing.

### Files and calculator variables (`file.h`, `mcs.h`)
* Files: `File_Open("\\\\fls0\\game.sav", FILE_OPEN_READ | FILE_OPEN_WRITE | FILE_OPEN_CREATE)`, `File_Read/Write/Lseek/Close/Remove/Rename/Mkdir/Stat/FindFirst...`;
  `\\fls0\` is the storage that appears as a USB drive on a PC (escape the backslashes in C strings). Returns < 0 on error - always check, and `File_Close` on every path.
  This is the place for **save files / high scores**: see `save.cpp` (fixed-size record with a magic + checksum so a bad file is ignored; opens for write without
  `FILE_OPEN_CREATE` first and falls back to creating it, so it works whether or not the OS truncates on open). **(unverified on hardware)** the exact open/truncate
  behaviour and that `\\fls0\` is writable from an app; the game simply shows "NEW HIGH (NOT SAVED)" if a write fails.
* `MCS_*`: read/write the calculator's own variables (lists, folders) - only needed for interop with the OS apps.

### Other
`String_Strlen/Strcpy/Strcmp/Strcat/Strchr`, `Battery_GetVoltage()` (`misc.h`, centivolts), `Serial_*` (link port), `GUI_DisplayMessageBox` and the C++ widgets in
`sdk/os/gui/*.hpp` (buttons, labels, dialogs). The Chess and Dino projects skip the widgets and draw everything themselves.

## 4. Performance rules (what actually mattered)

1. **No floating point, ever.** There is no FPU: every `float`/`double` operation is a library call. Use integers and **fixed point** (Q16 = value * 65536).
   `constexpr double` expressions evaluated at compile time are fine (`(q16)(5.7 * 65536)`). Check the object code: `make fpucheck` here, or on the host
   `g++ -O2 -S file.cpp && grep -E "mulsd|addsd|cvtsi2sd" file.s`.
2. **Avoid `/` and `%` by non-constants in hot paths** (there is no 32-bit hardware divide; the compiler calls a routine). Divisions by constants are fine.
   64-bit multiplies (`(int64_t)a*b >> 16`) are OK occasionally, not per pixel.
3. **`LCD_Refresh()` dominates the frame**: it always moves the whole 338 KB screen. Everything you can do on the CPU (clear, sprites, text) is small next to it.
   So: redraw only what changed, do not push frames when nothing moves, and consider a partial window update (section 3, "unverified").
4. **Write VRAM directly** (`uint16_t*`). Fill with 32-bit stores (`pair(color)` in two halves, `may_alias` `uint32_t*`), see `gfx::fillSpan`. Never call `LCD_SetPixel` per pixel.
5. **Pre-process sprites once** at start-up into run-length rows (`shapes.cpp`): drawing is then one tight loop per run instead of one test per pixel.
   Per-row left/right extents give cheap pixel-accurate collision.
6. **Draw only the dirty region.** Here the playfield strip is repainted every frame (it is small); the button panel is painted only when it changes.
7. Fixed arrays, no allocation in the game loop, no `std::` containers, no exceptions/RTTI, small `int` types for state.
8. Keep game rules **pure** (no SDK calls, no drawing) so they can run in unit tests on a PC at millions of ticks per second (`test/test_game.cpp`).

## 5. Game-loop template

```cpp
int main() {
    gfx::init();                                   // grab the VRAM pointer
    game::init();
    bool quit = false;
    while (!quit) {
        const bool idle = !game::animating();      // pause screen / menu
        for (int n = 0; n < 32; ++n) {             // 1. drain events
            struct Input_Event ev; zero(ev);
            GetInput(&ev, (n == 0 && idle) ? 0xFFFFFFFF : 0, 0x10);
            if (ev.type == EVENT_KEY && ev.data.key.direction == KEY_PRESSED) { if (ev.data.key.keyCode == KEYCODE_POWER_CLEAR) quit = true; /* ... */ }
            else if (ev.type == EVENT_TOUCH) { /* ... */ }
            else break;                            // EVENT_NONE
        }
        game::step(inputs);                        // 2. update (fixed timestep: one call = one tick)
        render(game);                              // 3. draw into VRAM
        LCD_Refresh();                             // 4. present (this also paces the loop)
        pace();                                    // 5. optional busy-wait, see section 6
    }
    return 0;                                      // calcExit restores the OS screen
}
```

## 6. Timing without a timer (important design constraint)

The SDK has **no clock or sleep function**. `EVENT_TIMER` exists but its period is unknown; the SH-4A's on-chip timers/RTC are not exposed, and this
CPU variant's register map is not documented in the SDK, so poking hardware registers blindly is a bad idea. What the projects do:

* **Frame-based time**: one loop pass = one tick; the speed is whatever one frame costs. `LCD_Refresh` is a fairly constant cost, so this is stable
  on one calculator but differs between models/OS versions. Game of Life exposes "speed" in frames; the Dino game uses **fixed-step ticks**
  (60 ticks/second is the design target, all constants in `game.cpp`).
* **A user-tunable busy-wait** at the end of the frame (`spin()` in `main.cpp`, "SPEED 1-9" setting) lets the player calibrate pace once.
  Use a `volatile` counter so the optimizer keeps the loop.
* Design speeds/accelerations in "per tick" units, keep everything integer, and never make game rules depend on how long a frame took.
* If you later find a safe time source (an RTC syscall, a documented register), only `pace()` has to change.

## 7. Testing on a PC (no calculator needed)

Because the SDK is "just headers + function pointers", the real app source can run on a PC:

* Compile `main.cpp` unchanged with `-DDINO_HOST -Dmain=dino_main -I$SDK_DIR/include`, and in a harness *define the function pointers the app uses*:
  ```cpp
  int  (*GetInput)(struct Input_Event*, uint32_t, uint32_t) = my_scripted_input;
  bool (*Input_GetKeyStateU)(uint16_t*) __asm__("Input_GetKeyState") = my_keystate;
  void (*LCD_Refresh)() = copy_vram_to_fake_panel;
  uint16_t* (*_FP_LCD_GetVRAMAddress)() __asm__("LCD_GetVRAMAddress") = return_fake_vram;
  ```
  (`vram` in `calc.h` is a fixed address, so the app takes its framebuffer pointer through one `init()` that switches on `DINO_HOST`.)
* The harness feeds a script (`key UP`, `tap 100 300`, `hold DOWN 15`, `frames 60`, `shot name`), writes PPM screenshots and a script converts them to PNG.
  This makes UI work and layout debugging possible from a terminal and in CI. See `test/host_app.cpp`, `test/script.txt`.
* Unit-test the rules with a **look-ahead bot** that plays millions of ticks using only the human controls (`test/bot.h`): it proves that the spawner never
  produces an unwinnable pattern and caught three real tuning problems here (jump airtime vs. minimum gap, a fast-fall bug, a collision bug).
* Check for stray soft-float and out-of-strip drawing (sentinel pixels) in tests. Remember that host results say nothing about real frame times.

## 8. Project layout that worked

```
main.cpp           SDK glue only: input, UI, loop, pacing           (the only file that needs the SDK headers, plus gfx.cpp)
game.h/.cpp        rules, fixed point, deterministic RNG (xorshift), no SDK
render.h/.cpp      state -> pixels
shapes.h/.cpp      art -> run-length sprites + collision extents
art.h              ASCII-art sprites ('#' = ink)  (easy to edit and review in diffs)
gfx.h/.cpp         framebuffer helpers + 5x7 font
Makefile           CP400 build (hh3)         test/Makefile   host tests
.github/workflows  CI: host tests + container build
```

## 9. Gotchas

* Zero `Input_Event` before `GetInput`; `GetInput` always returns 0 - look at `ev.type`.
* Touch coordinates can be outside the screen; clamp or reject.
* `KEYCODE_*` (events) and `Scancode*` (`Input_GetKeyState`) are different numbering.
* Give the player a quit key; an app that never returns needs a hard reset.
* The OS may draw over VRAM if you let it run (dialogs); `LCD_VRAMBackup/Restore` exist for that.
* The hollyhock-2 fork notes say the launcher is disabled in exam mode; do not promise games in exam mode.
* `calc.h`'s `color()` is slightly wrong (see section 3); `setPixel` there is bounds-checked and slow.
* An integer `a % b` or `a / b` with variable `b` pulls in a division routine; for random numbers use xorshift and `% constant`.
* Big-endian: when casting between `uint16_t` and `uint32_t` pixel pairs, build the 32-bit value as `(c << 16) | c` (symmetric, so safe).
* The linker option `--gc-sections` plus `-ffunction-sections` removes unused code; all three projects' Makefiles use `-ffat-lto-objects`, so keep it unless you test without it.
* A repo that is built only in CI cannot be tested locally without the toolchain; keep the host test target working so changes are checked everywhere.

## 10. Not known / worth testing on a real calculator

* Real frame time of `LCD_Refresh()` and the exact speed of one `spin()` unit (hence the user-tunable pace).
* Semantics of the partial-update window (`LCD_SetDrawingBounds`) on every hardware revision.
* Whether a timer period can be derived from `EVENT_TIMER`.
* Stack size available to the app (keep large buffers static, not on the stack).
